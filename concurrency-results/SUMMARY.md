## 3. 측정 경계
- 시작: 첫 `submit` 직전(`System.nanoTime`). 끝: 100개 Future 결과를 모두 수집한 직후(또는 30초 제한 도달 시점).
- 포함: 32개 워커 스레드 생성, 100건 submit, 트랜잭션 처리, 완료 대기.
- 제외: Spring 앱 기동, 계좌 생성, 사후 검증(잔액·원장·이력 조회).
- 이 값은 **100건 작업의 전체 완료시간**이다. 개별 요청 응답시간이나 운영 처리량이 아니다.
- 100건은 32개 스레드 풀에 제출된 것으로, 정확히 동시에 실행된 것이 아니다(최대 32개 동시 진행).

## 5. 코드 변경 내역과 이유 (업무 로직 `src/main` 변경 없음)
`ConcurrentTransferTest.java`만 재작성. 이전 버전은 `ConcurrentTransferTest.before.java.txt`로 보존.
| 변경 | 이유 |
|---|---|
| 예외를 출력만 하고 무시하던 것을 Future 결과로 수집, 성공/실패/미완료 집계 | 100건 전부 성공했는지 확인. 이전엔 실패가 잔액 검증에서만 간접적으로 드러날 수 있었음 |
| 제출 100 / 성공 100 / 실패 0 / 방향별 성공(50/50) 단언 | 양방향에서 반대 방향 실패가 상쇄되어 잔액이 맞아 보이는 경우를 차단 |
| 30초 전체 제한 + 타임아웃·미완료 수 기록, `shutdownNow`+`awaitTermination` | 대기 무한 방지, 스레드 정리 |
| 원장을 계좌·타입별 건수/합계로 검증(테스트 계좌 ID 한정), 이전엔 `findAll()` 후 필터 | 거래당 DEBIT/CREDIT 각 1건 구조를 건수까지 확인. 전체 테이블 조회 제거 |
| 송금 이력(`transfers`) 건수를 sender/receiver/type별로 검증 | 이력 100건 생성 및 방향 검증 |
| 조회용으로 `JdbcTemplate` SELECT만 사용 | `LedgerPort`/`TransferPort`에 계좌별 조회가 없어 프로덕션 코드 추가 대신 테스트 내부 조회로 처리 |
| 시나리오별 10회 반복, 회차마다 새 계좌, 실패 회차도 CSV 기록 후 마지막에 단언 | 실패를 숨기지 않기 위함 |
| 예외는 유형+메시지(120자 제한)만 기록 | 민감정보 제외 |
데이터 삭제·전체 테이블 초기화·`sleep` 사용 없음.

## 6. 검증 완료 / 미검증
검증 완료(H2, 20회 전부): 요청 수·성공·실패·미완료, 방향별 성공 수, 최종 잔액, 잔액 합계 보존, 원장 DEBIT/CREDIT 계좌별 건수·합계, 송금 이력 건수·방향, 30초 내 완료.

미검증:
- **MySQL 실행**: 3306 포트에 리스너가 없고 Docker도 없어 격리된 테스트 MySQL을 확인하지 못했다. 미실행. (운영/개발 DB에는 연결하지 않음. 주의: `src/main`의 설정은 `ddl-auto=create`이므로 격리 DB 없이 붙이면 안 됨)
- **거래 단위 원장 대응**: 원장과 송금 이력 사이에 연결 키(transfer id)가 없어, 개별 거래 ↔ 원장 2건의 1:1 매핑은 확인 불가. 계좌·방향별 총량으로만 검증.
- 데드락이 절대 발생하지 않는다는 보장: 아님. 이 조건(H2, 2계좌, 32스레드)에서 20회 타임아웃이 없었다는 관측이다.
- 다계좌·장시간·운영 규모 부하, 개선 전후 비교(개선 전 측정 없음).

## 7. 자기소개서용 사실 문장
1. 계좌 ID 오름차순 비관적 락을 적용한 송금 로직을 H2 인메모리 환경에서, 32개 스레드 풀에 100건을 제출하는 단일방향·양방향(A↔B 각 50건) 시나리오로 각 10회 검증해, 매회 100건 모두 성공하고 실패·타임아웃이 없었으며 최종 잔액이 기대값과 일치함을 확인했다.
2. 잔액 일치만으로는 양방향 송금의 실패가 상쇄되어 가려질 수 있어, 요청별 성공 여부와 방향별 성공 건수, 원장 DEBIT/CREDIT 합계·건수(각 100,000원·100건), 송금 이력 건수까지 함께 검증하도록 테스트를 보완했다.
3. 100건 처리 전체 완료시간은 단일방향 중앙값 279ms, 양방향 중앙값 198ms(H2, 로컬 환경 기준)였다. 이는 MySQL이나 운영 환경의 성능이 아니다.
