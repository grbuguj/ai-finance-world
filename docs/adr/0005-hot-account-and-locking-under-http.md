# ADR-0005. 계좌 락은 DB 행 락만 쓰고, OSIV 는 끈다 (E2E 부하에서 드러난 두 결함)

- 상태: 채택
- 근거: CI `E2E (docker compose + k6)` 잡 — 앱·MySQL·Redis·Kafka 컨테이너 전체 스택에 k6 로 실제 HTTP 부하
- 관련 코드: `application.properties`(`spring.jpa.open-in-view`, `app.lock.distributed.enabled`),
  `AccountLockExecutor`, `RedisDistributedLockAdapter`, `HttpSpendConcurrencyTest`

## 증상
전체 스택 E2E 를 처음 붙였을 때 `mixed` 시나리오(요청의 60% 가 가맹점 5곳으로 결제, VUS 30)가 비정상이었다.

| | TPS | p99 | 실패율 |
|---|---:|---:|---:|
| transfer (송금만) | 205 | 765ms | 0% |
| **mixed (결제 60%)** | **24** | **4,203ms** | **26.6%** |

원장 무결성과 대사는 맞았다(돈은 새지 않음). 하지만 결제 4건 중 1건이 실패했다.

## 원인 1 — OSIV 가 낡은 계좌 엔티티를 재사용하게 만듦 (실패율의 원인)
분산 락 방식을 바꿔도 실패율이 25% 그대로라서 락이 원인이 아님을 먼저 확인했다. 이어서 **HTTP 를 거치지 않고 서비스를 직접 부르면 같은 부하가 400/400 성공**하는 대조 실험으로 HTTP 경로에 원인을 좁혔다.

1. Spring Boot 기본값인 OSIV(Open Session In View)는 HTTP 요청 내내 영속성 컨텍스트를 유지한다.
2. `SpendUseCase` 는 가맹점 유효성을 확인하려고 **락 없이 계좌를 먼저 읽는다** → 요청 범위 컨텍스트에 남는다.
3. 이후 기장 트랜잭션의 `SELECT … FOR UPDATE` 는 행 락은 잡지만, Hibernate 가 이미 관리 중인 엔티티를 **갱신하지 않고 그대로 반환**한다 → 낡은 잔액·버전.
4. 낡은 값으로 계산해 저장하면 `@Version` 충돌(`StaleStateException`)로 실패.
   **`@Version` 이 없었다면 가맹점 잔액을 조용히 덮어쓰는 Lost Update** 가 됐을 경로다.

서비스 메서드를 직접 부르는 기존 테스트와 시뮬레이션 엔진은 OSIV 가 적용되지 않아 드러나지 않았다.
테스트용 `application.properties` 가 main 설정을 통째로 가리는 바람에, 처음 수정 후에도 HTTP 테스트에서는 OSIV 가 켜져 있었던 것도 원인 확정 과정에서 발견했다.

**조치**: `spring.jpa.open-in-view=false` (연관관계가 모두 EAGER 라 지연 로딩 영향 없음),
버전 충돌은 500 대신 409 + 재시도 안내. `HttpSpendConcurrencyTest` — 실제 HTTP 로 같은 가맹점에 동시 결제 400건 → 전량 성공 + 무결성.

## 원인 2 — 공정성 없는 Redis 스핀 락이 핫 계좌의 꼬리 지연을 키움
OSIV 수정 후 같은 E2E 에서 계좌 락 방식만 바꿔 측정했다 (각 30초, 앱을 설정만 바꿔 재기동).

| 계좌 락 방식 | TPS | p95 | p99 | 실패율 |
|---|---:|---:|---:|---:|
| Redis 스핀 락 (백오프 최대 50ms) → DB 행 락 | 200.1 | 623ms | 1,245ms | 0.02% |
| Redis 스핀 락 (백오프 최대 5ms + 지터) → DB 행 락 | 186.5 | 591ms | 1,121ms | 0% |
| **DB 행 락만** (`SELECT … FOR UPDATE`, ID 오름차순) | **280.3** | **257ms** | **412ms** | 0% |

- 스핀 락에는 대기 순서가 없다. 락이 풀린 순간 마침 깨어 있던 요청이 가져가고, 운 나쁜 요청은 계속 밀린다.
  백오프를 줄이면 Redis 왕복만 늘고 개선되지 않았다.
- InnoDB 행 락 대기는 사실상 도착 순서대로 처리되어 꼬리 지연이 짧다.
- 이 시스템은 DB 가 하나라서 **정합성은 DB 행 락이 보장**한다. 앞단의 분산 락은 정합성에 보태는 것 없이 지연만 더했다.

**결정**: 계좌 락 기본값을 DB 행 락만으로 한다 (`app.lock.distributed.enabled=false`).
Redis 는 Outbox 릴레이의 단일 실행 락과 잔액 캐시에 계속 쓴다. 계좌 분산 락은 설정으로 다시 켤 수 있게 남긴다.

## 결과 (같은 E2E, 수정 전 → 후)
| mixed | TPS | p99 | 실패율 |
|---|---:|---:|---:|
| 수정 전 | 24.4 | 4,203ms | 26.6% |
| 수정 후 | 280.3 | 412ms | 0% |

## 다시 분산 락이 필요해지는 경우
- 계좌 데이터를 여러 DB 로 샤딩해 한 거래가 여러 DB 의 행을 잠가야 할 때
- DB 밖의 자원(외부 API 호출 한도 등)을 함께 직렬화해야 할 때
- 그때도 스핀 락이 아니라 대기열·알림 기반 락(예: Redisson 의 공정 락)이나 계좌별 단일 스레드 큐를 검토한다.

## 교훈
- 서비스 메서드를 직접 부르는 테스트는 웹 계층의 동작(OSIV, 필터, 직렬화)을 검증하지 못한다 → 실제 HTTP 동시성 테스트를 둔다.
- 방어 장치(`@Version`)는 "실패로 드러나게" 해 줬다. 없었다면 같은 버그가 조용한 잔액 오류였을 것이다.
- "분산 락은 많을수록 안전하다"는 직관은 측정 앞에서 틀렸다. 정합성의 근거가 어디에 있는지 먼저 정한다.
