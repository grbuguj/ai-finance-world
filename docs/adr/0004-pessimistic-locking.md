# ADR-0004. 잔액 갱신은 비관적 락 + 계좌 ID 오름차순을 유지한다 (실험 근거)

- 상태: 채택 (기존 결정을 실험으로 재검증)
- 근거: [실험 보고서 — 락 전략 비교와 낙관적 락 Lost Update](../experiments/lock-strategy-benchmark.md)

## 문제
"왜 낙관적 락이 아니라 비관적 락인가?"는 면접·심사에서 반드시 나오는 질문이다. 감이 아니라 같은 조건의 측정값으로 답해야 한다.

## 결정
서비스 기장 경로(`LedgerPostingService`)는 `SELECT … FOR UPDATE`(계좌 ID 오름차순) + 도메인 객체 갱신을 유지한다.

## 근거 (MySQL 8.0, 32 스레드, 실행당 2,000건)
| 관점 | 비관적 락 | 낙관적 락 |
|---|---|---|
| 핫스팟 처리량 | 731 TPS | 187 TPS |
| 핫스팟 p99 | 50ms | 822ms |
| 핫스팟 실패율 | 0% | 5.3% (재시도 한도 초과) |
| 정합성 | 전 시나리오 위반 0 | REPEATABLE READ + 읽은 값 덮어쓰기 구현에서 Lost Update 관측 (약 1만 커밋당 1건, READ COMMITTED 에서는 0건) |

- 금융 거래는 특정 계좌(가맹점, 인기 수취인)에 쓰기가 몰린다. 경합이 높은 곳에서 낙관적 락은 재시도 폭주로 느려지고 실패한다.
- 비관적 락은 대기열이라 느려지더라도 꼬리 지연이 안정적이고 실패가 없다.
- 계좌 ID 오름차순 획득으로 PINGPONG(서로 동시 송금)에서도 데드락 0건.

## 함께 내린 결정
- `Account` 에 `@Version` 추가 — 비관적 락을 우회한 갱신이 생기면 덮어쓰기 대신 예외로 드러나게 하는 이중 방어.
- 금액 갱신 SQL 을 직접 쓸 때는 읽은 값을 덮어쓰지 않고 `balance = balance ± ?` 로 쓴다 (실험에서 관측된 Lost Update 의 교훈).
- 쓰기가 몰리는 계좌는 락 방식보다 **서브계좌 분산**이 효과적이다 (같은 비관적 락에서 TPS 2.3배). 가맹점 계좌 분산은 후속 과제.

## 기각한 대안
| 대안 | 기각 이유 |
|---|---|
| 낙관적 락 + 재시도 | 핫스팟에서 처리량 1/4, p99 16배, 실패 5%. 정합성 위험 관측 |
| 조건부 UPDATE (`WHERE balance >= ?`) | 가장 빠르지만 단일 행 조건만 표현 가능 → 도메인 규칙이 SQL 로 흩어짐. 단순 적립 경로 최적화 후보로 보류 |
| Redis 분산 락만 사용 | DB 와 별개 시스템이라 락 만료·장애 시 정합성을 DB 가 보장하지 못함. 다중 인스턴스 대비 보조 수단으로만 유지 |
