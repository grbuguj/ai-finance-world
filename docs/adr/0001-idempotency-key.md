# ADR-0001. 멱등성 키로 중복 요청을 막는다

- 상태: 채택
- 관련 코드: `IdempotentExecutor`, `IdempotencyJpaAdapter`, `IdempotencyTest`

## 문제
모바일 앱이 송금 요청을 보냈는데 응답 직전에 네트워크가 끊기면, 앱은 송금이 됐는지 알 수 없어 같은 요청을 다시 보낸다.
서버가 이를 새 요청으로 처리하면 **돈이 두 번 빠진다.** 비관적 락은 "동시에 들어온 서로 다른 요청"의 정합성은 지켜주지만,
"같은 의도의 요청이 두 번 온 것"은 구분하지 못한다.

## 결정
클라이언트가 요청마다 고유한 `Idempotency-Key` 헤더를 보내고, 서버는 키를 **거래와 같은 DB 트랜잭션**에 저장한다.

```
[분산 락] → 트랜잭션 {
    INSERT idempotency_keys(key, request_hash)   ← PK 유니크 제약이 중복을 막는 지점
    기장 (계좌 락 → DEBIT/CREDIT)
    UPDATE idempotency_keys SET transfer_id = ?
} 커밋
```
- 같은 키가 이미 있으면 기장하지 않고 저장된 거래를 돌려준다 (`Idempotent-Replayed: true`).
- 같은 키가 동시에 들어오면 InnoDB 가 두 번째 INSERT 를 첫 트랜잭션 커밋까지 대기시킨 뒤 중복 키 오류를 낸다.
  패배한 요청은 롤백 후 첫 요청의 결과를 조회해 같은 응답을 돌려준다.
- 같은 키에 요청 내용(계좌·금액·유형 해시)이 다르면 422 로 거절한다.

## 검토한 대안
| 대안 | 기각 이유 |
|---|---|
| Redis 에 키 저장 (`SET NX`) | 키 저장과 거래 커밋이 원자적이지 않다. 키만 저장되고 서버가 죽으면 재시도가 영원히 막히고, 반대 순서면 이중 출금 |
| 키를 별도 트랜잭션에서 먼저 저장 | 위와 같은 문제 + "처리 중" 상태 관리와 타임아웃 복구가 필요해 복잡도 증가 |
| 거래 테이블에 키 컬럼 + 유니크 | 가능하지만 거래 유형마다 테이블이 늘면 중복 구현. 키 테이블을 분리해 모든 유형에 재사용 |

## 결과
- 키와 거래가 함께 커밋/롤백되므로 "돈은 나갔는데 키가 없다" 또는 "키는 있는데 돈은 안 나갔다"가 구조적으로 불가능하다.
- 실패한 요청(잔액 부족 등)은 키도 롤백되어 같은 키로 재시도할 수 있다.
- 키는 24시간 보관 후 정리한다 (`IdempotencyKeyCleaner`).
- 검증: 같은 키 50건 동시 전송 → 실제 송금 1건, 50건 모두 같은 거래 id 응답 (`IdempotencyTest`, MySQL: `MySqlIdempotencyTest`).
