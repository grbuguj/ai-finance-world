# 앱 2대 동시 실행 실험

같은 DB(MySQL)·Redis·Kafka 를 보는 앱 인스턴스 2대(8080, 8081)에 HTTP 부하를 나눠 보냈을 때 무엇이 안전하고 무엇이 안전하지 않은지 확인한다.
**수치는 실제로 돌린 값만 적고, 돌리지 못한 값은 "미실행"으로 적는다. 문제가 발견되면 그대로 기록한다(그 자체가 결과다).**

## 구성

- `docker-compose.yml`: `app`(8080) + `app2`(8081, `--profile app2`). 같은 MySQL/Redis/Kafka.
- 엔진은 양쪽 모두 정지(`APP_SIMULATION_AUTO_START=false` + `/loadtest/setup` 의 `stop()`)해 가상 시계를 고정하고, 부하는 k6 와 같은 HTTP 송금으로만 준다.
  **가상 자정 대사는 이 시나리오의 범위가 아니다** (아래 "코드에서 확인한 구조적 위험" 3번 참고).
- 두 변형: `redis-on`(릴레이 분산 락 있음), `redis-off`(락이 no-op).
- 도구: `tools/experiments/multi_instance.py`, workflow `multi-instance.yml` (수동 실행, 결과는 `experiment-results` 브랜치).

## 코드에서 확인한 구조적 위험 (실험 전에 읽어서 알아낸 것)

실측이 아니라 코드 읽기로 확인한 사실이다.

1. **릴레이 락은 Redis 가 꺼지면 항상 성공한다.** `OutboxRelayService.relayOnce()` 는 `DistributedLockPort.tryLock("lock:outbox-relay", 대기 0, 임대 30초)` 를 쓴다.
   `app.redis.enabled=false`(기본값)이면 `NoOpCacheConfig` 가 항상 "획득 성공"을 돌려주므로, **앱 2대의 릴레이가 동시에 돌아 같은 PENDING 이벤트를 둘 다 읽을 수 있다.**
   `OutboxRepository.findPublishable` 에는 `FOR UPDATE SKIP LOCKED` 도 없다. 즉 단일 발행을 보장하는 장치는 Redis 락 하나뿐이다.
2. **중복 발행은 멱등 소비자가 흡수한다.** 위 1번으로 같은 이벤트가 두 번 나가도 `SettlementInbox` 가 transfer id 로 걸러 정산 장부에는 한 줄만 남는다
   (`delivery_count` 가 흡수한 횟수). 그래서 방어선이 두 겹이다: ① 릴레이 락(중복 발행 자체를 줄임) ② 멱등 소비자(발행이 중복돼도 정산은 한 번).
   다만 같은 키(보내는 계좌)의 **순서**는 두 릴레이가 동시에 발행하면 보장되지 않는다 — 멱등 소비자는 순서를 고치지 못한다.
3. **엔진 상태·가상 시계·틱은 JVM 메모리에 있다.** 앱마다 `VirtualClock` 이 따로 있어서, 한 앱만 틱을 돌리면 다른 앱의 HTTP 거래는 `occurred_at` 이 틱 0 시각으로 찍힌다.
   그래서 이 실험은 엔진을 양쪽 다 꺼 시계를 고정했다. 엔진을 2대에서 모두 켜면 같은 에이전트를 두 앱이 각자 움직인다 — 리더 선출이 없다.
4. **스키마 생성이 위험하다.** 기본 `spring.jpa.hibernate.ddl-auto=create` 라서 2번째 앱을 기동하면 **DB 를 지우고 다시 만든다.** 그래서 `app2` 는 `ddl-auto=none` 이고 첫 앱이 healthy 해진 뒤에 기동한다.
5. **기동 시 월드 생성 경합.** `bootstrap=true` 면 두 앱이 동시에 뜰 때 `initialize()` 가 둘 다 `existing==0` 으로 보고 시스템 계좌를 중복 생성할 수 있다 (순차 기동으로 회피).
6. **Kafka 소비자.** 토픽이 파티션 1개로 자동 생성되면 같은 consumer group(`external-settlement`) 의 앱 2대 중 한 대만 소비한다. 그 앱이 죽으면 리밸런스 시간만큼 정산 수신이 멈춘다.

## 시나리오

1. **부하 분산**: 두 앱에 HTTP 부하를 나눠 보낸 뒤 Outbox 발행 건수, 정산 수신 건수, 중복 수신(멱등이 흡수한 수), 키별 순서 위반, 대사 결과를 기록.
2. **브로커 장애**: 두 앱 모두 `/chaos/broker/down` → 부하 → `up` → 대사 MATCHED 확인.
3. **인계 시간**: 릴레이 락을 잡고 있는 순간(Redis 키 `lock:outbox-relay` 가 보일 때) 그 앱을 `docker kill` → 다른 앱이 락(임대 30초)을 이어받는 데 걸린 시간.

## 실측 결과 (CI: GitHub Actions ubuntu-latest, docker compose, 앱 2대, 20 스레드, 시나리오당 부하 25초)

원본: `experiment-results` 브랜치 `multi-instance/44700299699/` (`multi-instance-redis-on.json`, `multi-instance-redis-off.json`, 앱 로그). 엔진 상태는 앱1 ENDED, 앱2 PAUSED(둘 다 정지, 가상 시계 고정).

### 시나리오 1: 부하 분산 (두 앱에 HTTP 부하를 반반)

| 항목 | redis-on (릴레이 락 있음) | redis-off (락 no-op) |
|---|---|---|
| 요청 / 성공 | 4,101 / 4,101 | 3,697 / 3,697 |
| Outbox 발행 건수 | 4,101 | 3,697 |
| 정산 수신(정산 장부 행) | 4,101 | 3,697 |
| **중복 수신 (멱등 소비자가 흡수한 수)** | **0** | **2,939** (발행 건수의 약 79%) |
| 키별 순서 위반 | 0 | 0 |
| 비우는 데 걸린 시간 | 12.9 초 | 18.9 초 |
| 대사 | MATCHED (4,211 = 4,211) | MATCHED (3,807 = 3,807) |

- **Redis 락이 있으면 중복이 0, 없으면 같은 이벤트가 두 번 이상 발행돼 79%가 중복 수신됐다.** 두 릴레이가 같은 PENDING 이벤트를 동시에 읽어 둘 다 발행한 것이다(코드에서 예상한 대로).
- 하지만 redis-off 에서도 **정산 장부 행 수는 발행 수와 같고 대사는 MATCHED** 다 — 멱등 소비자(`SettlementInbox`)가 중복 2,939건을 모두 흡수했다.
  이것이 "방어선이 두 겹"이라는 서술의 근거다: ① 릴레이 락(중복 발행을 줄임) ② 멱등 소비자(발행이 중복돼도 정산은 한 번). 락이 꺼져도 정합성은 유지되지만 비용(중복 트래픽·처리)이 든다.

### 시나리오 2: 브로커 장애 (두 앱 모두 down → 부하 → up)

| 항목 | redis-on | redis-off |
|---|---|---|
| 요청 / 성공 | 9,230 / 9,230 (장애 중에도 거래는 계속 성공) | 8,614 / 8,614 |
| 장애 종료 시 Outbox 대기 | 9,230 | 8,614 |
| `up` 후 비우는 데 걸린 시간 | 16.5 초 | 34.6 초 |
| 중복 수신 | 0 | 7,992 (발행 건수의 약 93%) |
| **키별 순서 위반** | **50** | **41** |
| 대사 | MATCHED (13,441 = 13,441) | MATCHED (12,421 = 12,421) |

- **발견: redis-on 에서도 순서 위반이 50건 있었다.** 시나리오 1(장애 없음)에서는 0건이다. 장애로 이벤트마다 실패 횟수가 달라 `next_attempt_at`(지수 백오프)이 서로 달라지고,
  복구 후 백오프가 먼저 끝난 이벤트가 id 가 앞선 이벤트(아직 백오프 중)보다 먼저 발행되는 것이 원인으로 **추정**된다. **이 원인은 이번에 검증하지 않았다**
  (앱 1대로 같은 시나리오를 돌려 비교하지 않았으므로 "2대라서 생긴 문제"인지 "백오프 때문에 1대에서도 생기는 문제"인지 구분하지 못한다).
  정산 시스템은 transfer id 로 멱등 처리하므로 장부 정합성에는 영향이 없지만, "같은 키(보내는 계좌) 순서 보장"이라는 Outbox 설명(ADR-0002)은 장애 복구 직후에는 성립하지 않는다.
- redis-off 의 순서 위반 41건은 위 원인과 동시 발행이 섞인 값이라 따로 해석하지 않는다.

### 시나리오 3: 릴레이 락 보유 앱 강제 종료 → 인계 (redis-on)

| 항목 | 값 |
|---|---|
| 강제 종료 대상 | 앱1 (`docker kill`), 락 키 `lock:outbox-relay` 가 보이는 순간 |
| 종료 직후 락 남은 시간(PTTL) | 29,188 ms (임대 30초) |
| **인계 시간 (종료 → 다른 앱이 락 획득)** | **30.11 초** (= 락 임대 만료를 기다린 시간) |
| 이후 밀린 이벤트를 비우는 데 걸린 시간 | 99.5 초 |
| 무결성 / 대사 | balanced=true / MATCHED (45,352 = 45,352) |

- 인계는 **락 임대 시간(30초)이 상한**이다. 락을 쥔 앱이 죽으면 최대 30초 동안 모든 인스턴스의 릴레이가 멈춘다. 이 시간은 `RELAY_LOCK` 임대(`Duration.ofSeconds(30)`)를 줄이면 짧아지지만,
  한 배치 발행이 임대보다 오래 걸리면 두 릴레이가 겹칠 수 있어(위 redis-off 와 같은 중복·순서 문제) 줄이는 것은 트레이드오프다.
- 99.5초는 인계 후 Outbox 를 비우는 시간만이 아니라, 죽은 앱이 소비자 그룹에서 빠지는 시간(Kafka 리밸런스)과 밀린 이벤트 처리량이 섞인 값이다. 둘을 분리해 측정하지 않았다.

### 이 실험으로 확인된 위험 (코드 읽기와 대조)

| 코드에서 예상 | 실측 |
|---|---|
| Redis 가 꺼지면 릴레이 락이 no-op 이라 2대가 동시 발행 | **확인**: 중복 2,939 / 7,992건 |
| 중복은 멱등 소비자가 흡수 | **확인**: 장부 행 수 = 발행 수, 대사 MATCHED |
| 단일 발행 보장은 Redis 락 하나뿐 (`SKIP LOCKED` 없음) | redis-on 중복 0 으로 락이 동작함을 확인. `SKIP LOCKED` 를 넣으면 락 없이도 중복 발행을 줄일 수 있다 — 구현하지 않았다 |
| 엔진·가상 시계는 JVM 별 상태 | 이 실험은 양쪽 엔진을 꺼서 회피. 두 앱에서 엔진을 켠 경우는 측정하지 않았다 |
| ddl-auto=create 가 2번째 앱 기동 시 DB 를 지움 | 측정하지 않고 회피(`app2` 는 `none`, 순차 기동) |
